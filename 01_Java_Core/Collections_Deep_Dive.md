# 📦 Глубокое погружение в Collections API & ConcurrentHashMap
#java-core #collections #concurrency #senior

### 🎯 Главный инсайт (TL;DR)
> Современные коллекции в Java оптимизированы под минимизацию блокировок. Эволюция `ConcurrentHashMap` от Java 7 к Java 8+ показывает фундаментальный сдвиг архитектуры: от тяжелых сегментов на базе Lock-интерфейсов к атомарным операциям (CAS) и точечным блокировкам отдельных корзин (Buckets).

### ⚙️ Архикетурные особенности (Under the Hood)

#### 1. Внутреннее устройство HashMap (База)
*   Представляет собой массив корзин (Buckets), где каждый элемент — это связный список (Node).
*   **Дерево вместо списка (Java 8+):** Если в одной корзине из-за коллизий хэш-функции количество элементов превышает `TREEIFY_THRESHOLD = 8`, а общий размер массива больше 64, связный список автоматически перестраивается в красно-черное дерево (TreeNode). Это гарантирует падение худшей скорости поиска с O(N) до \(O(\log N)\).
*   **Формула индекса:** Позиция в массиве вычисляется как `(n - 1) & hash`. Размер массива (`n`) всегда является **степенью двойки**, чтобы дорогое деление по модулю `%` заменить на ультрабыструю побитовую операцию `&`.

#### 2. Революция ConcurrentHashMap: Java 7 vs Java 8+
Интервьюеры обожают спрашивать разницу между старой и новой реализацией.

```text
Java 7 (Segment Locking):
[Segment 1 (ReentrantLock)] -> [Buckets...]
[Segment 2 (ReentrantLock)] -> [Buckets...]  // Блокируется весь сегмент целиком

Java 8+ (Fine-Grained / CAS Locking):
[Bucket 1] -> Использует CAS (без блокировок) для первой вставки Node
[Bucket 2] -> Потоки блокируют только первую ноду через synchronized (Точечный Lock)
```

*   **В Java 7** использовался паттерн **Segment Locking**. Карта делилась на 16 независимых сегментов, каждый из которых наследовался от `ReentrantLock`. Потоки могли параллельно писать в карту, только если они били в разные сегменты.
*   **В Java 8+** сегменты полностью удалили. Теперь массив корзин — это единый плоский массив. Блокировка стала **гранулярной (Fine-Grained)**:
    1. Если корзина пуста, первый элемент вставляется абсолютно без блокировок, с помощью атомарной инструкции процессора **CAS (Compare-And-Swap)**.
    2. Если в корзине уже есть элементы, поток блокирует только **первую ноду (Head Node)** этой конкретной корзины с помощью обычного встроенного `synchronized`. Все остальные корзины остаются полностью свободными для записи другими потоками.

### 💣 Ловушки на собеседованиях (Interview Traps)

*   ❌ **Вопрос:** «Можно ли передавать `ConcurrentHashMap` в качестве аргументов и ожидать, что любая последовательность операций с ним будет потокобезопасной?»
*   ✅ **Ответ:** **Нет, нельзя.** Потокобезопасными являются только атомарные методы самого класса (например, `.put()`, `.get()`, `.computeIfAbsent()`). Если вы делаете проверку и последующую запись вручную:
    ```java
    if (!map.containsKey(key)) { map.put(key, value); } // ТАК ДЕЛАТЬ НЕЛЬЗЯ!
    ```
    Между проверкой `containsKey` и вставкой `put` другой поток успеет вклиниться и перезаписать данные (Race Condition).
    *   💡 **Как лечить:** Использовать атомарные методы: `map.putIfAbsent(key, value)`.

*   ❌ **Вопрос:** «Почему `ConcurrentHashMap` запрещает использовать `null` в качестве ключа или значения, в то время как обычный `HashMap` это разрешает?»
*   ✅ **Ответ:** Это сделано для исключения двусмысленности в многопоточной среде, известной как **«Проблема Конкурентного Налла»**. Если метод `map.get(key)` вернет `null`, в обычном однопоточном коде это означает, что ключа нет. В многопоточной среде вы не можете быть в этом уверены: ключ отсутствовал в момент вызова, или другой поток только что удалил его/записал туда `null`? В конкурентной среде метод `containsKey(key)` после `get()` вызывать бессмысленно — состояние карты уже могло измениться.
