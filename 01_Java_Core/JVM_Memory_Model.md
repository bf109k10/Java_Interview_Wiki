# 🧠 Архитектура памяти JVM и Сборщики мусора (Garbage Collection)
#java-core #jvm #garbage-collection #senior

### 🎯 Главный инсайт (TL;DR)
> Память JVM строго разделена на области с разным жизненным циклом, а эволюция сборщиков мусора направлена на перевод тяжелых пауз (Stop-The-World) в параллельный (Concurrent) режим. Современный флагман **ZGC** утилизирует гигабайты памяти с задержками менее миллисекунды за счет применения цветных указателей и барьеров чтения.

### ⚙️ Архитектурные особенности (Under the Hood)

#### 1. Структура памяти JVM
*   **Heap (Куча):** Единая для всего приложения область. Здесь живут все объекты и массивы. Делится на *Young Generation* (Eden, Survivor пространства S0/S1) и *Old (Tenured) Generation*.
*   **Stack (Потоковый стек):** У каждого потока свой стек. Хранит фреймы выполнения методов, примитивы и ссылки на объекты в хипе. При переполнении вылетает `StackOverflowError`.
*   **Metaspace (Метаданные):** Пришел на смену PermGen. Находится в *native memory* (вне виртуальной кучи), хранит метаданные классов, структуры методов. Растет динамически, пока не упрется в физическую память ОС.

#### 2. Четыре типа ссылок в Java
Определяют, как GC будет взаимодействовать с объектом:
1.  **Strong Reference (`Object obj = new Object()`):** Стандартная ссылка. Объект никогда не будет удален, пока на него есть хоть одна такая ссылка.
2.  **Soft Reference (`SoftReference<O>`):** Объекты удаляются только тогда, когда у JVM **заканчивается память** (перед гарантированным OOM). Идеально для простых кэшей.
3.  **Weak Reference (`WeakReference<O>`):** Объект будет удален при **следующем же цикле сборки мусора**, независимо от объема свободной памяти. На них построена `WeakHashMap` (для метаданных или плагинов).
4.  **Phantom Reference (`PhantomReference<O>`):** Метод `.get()` всегда возвращает `null`. Используется вместо устаревшего и опасного метода `finalize()` для сложной очистки системных ресурсов (через `ReferenceQueue`), когда объект физически стерт из памяти.

#### 3. Битва титанов: G1 GC vs ZGC
*   **G1 (Garbage-First):** Сборщик по умолчанию с Java 9. Бьет кучу на тысячи мелких регионов. Собирает мусор в первую очередь там, где его больше всего. Имеет настраиваемую паузу Stop-The-World (STW), но на кучах >32 ГБ паузы могут вырастать до сотен миллисекунд.
*   **ZGC (Z Garbage Collector):** Масштабируемый сборщик со сверхнизкой задержкой (доступен как production-ready с Java 15, улучшен в Java 21+ через поколенческий режим Generational ZGC). 
    *   Все фазы (разметка, копирование, уплотнение кучи) происходят **параллельно с работой бизнес-потоков**. 
    *   Паузы STW фиксированы и **не превышают 1 миллисекунду** даже на терабайтных кучах.
    *   Достигается за счет **Colored Pointers (цветных указателей)**: метаданные о состоянии объекта (был ли он перемещен) хранятся прямо в старших битах 64-битной ссылки на объект, а потоки приложения при обращении к ссылке используют **Load Barriers (барьеры чтения)** для нахождения актуального адреса объекта.

### 💣 Ловушки на собеседованиях (Interview Traps)

*   ❌ **Вопрос:** «Где физически создаются и хранятся объекты в Java? Всегда ли они попадают в Heap?»
*   ✅ **Ответ:** **Не всегда.** Современный JIT-компилятор применяет оптимизацию **Escape Analysis (Анализ побега)**. Если компилятор видит, что объект создается внутри метода и ссылка на него никогда не «убегает» наружу (не возвращается как результат, не передается в другие потоки), то JVM может соптимизировать код и создать этот объект **прямо на стеке потока** (или разложить его на примитивные переменные в регистрах процессора — *Scalar Replacement*). При выходе из метода память очищается мгновенно без участия Garbage Collector.

*   ❌ **Вопрос:** «В чем опасность использования SoftReference для построения production-кэшей в высоконагруженных системах?»
*   ✅ **Ответ:** Поведение `SoftReference` сильно зависит от текущего давления на память (Memory Pressure) внутри JVM. Если ваше приложение попадет под жесткую нагрузку и память начнет поджимать, GC начнет агрессивно вычищать объекты по мягким ссылкам. В итоге ваш кэш мгновенно «протухнет» и превратится в тыкву в самый критический момент — вся лавина запросов пользователей пойдет напрямую в базу данных, создавая эффект лавины кэша (Cache Avalanche). 
*   💡 **Как лечить:** Использовать профессиональные кэш-библиотеки (Caffeine, Guava), контролирующие размер кэша по алгоритмам W-TinyLFU, а не полагаться на системные ссылки.
