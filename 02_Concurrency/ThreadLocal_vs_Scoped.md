# 🧬 Хранение контекста: Эволюция от ThreadLocal к Scoped Values (JEP 506)

### 🎯 Главный инсайт (TL;DR)
> В эпоху миллионов виртуальных потоков (Project Loom) классический `ThreadLocal` стал опасным антипаттерном из-за избыточного расхода памяти и риска утечек. Начиная с Java 25, его полностью заменяет механизм **Scoped Values (Связанные значения)**, который привязывает иммутабельные данные не к жизненному циклу потока, а к конкретной лексической области видимости кода.

### ⚙️ Архитектурные особенности (Under the Hood)

#### 1. Фундаментальный изъян `ThreadLocal`
Исторически `ThreadLocal` использовался фреймворками (Spring Security, Hibernate) для неявной передачи контекста (Security Context, Transaction ID) вниз по call-стеку. Каждому потоку выделялась своя мутабельная хэш-карта `ThreadLocalMap`.
При переходе на виртуальные потоки (Virtual Threads) это привело к катастрофам:
1.  **Прожорливость RAM:** Если у вас запущено 1 000 000 виртуальных потоков, и каждый поток удерживает в своей карте даже небольшие объекты, память JVM мгновенно исчерпывается (OOM).
2.  **Утечки памяти:** Метод `.set()` позволяет менять значение где угодно, а если разработчик забыл вызвать `.remove()`, объект зависает в памяти навсегда.
3.  **Оверхед на наследование:** При создании дочернего потока через `InheritableThreadLocal` вся карта родителя копировалась, нагружая CPU и RAM.

#### 2. Как работают Scoped Values (Java 25 Стандарт)
`ScopedValue` — это контейнер для безопасного шеринга данных, спроектированный с учетом требований Loom. 

```text
ThreadLocal:
[Поток] ──> 持有 (Хранит в себе) ──> [Мутабельная карта ThreadLocalMap] (Живет пока жив поток)

Scoped Value:
ScopedValue.where(KEY, VALUE).run(() -> { [Блок кода / Scope] }); 
(Данные доступны строго внутри лямбды и стираются автоматически при выходе из нее)
```

*   **Иммутабельность:** Значение `ScopedValue` можно задать только один раз при входе в scope. Метода `.set()` не существует. Изменить значение внутри блока невозможно, его можно только временно переопределить (Rebind) для более глубокого вложенного блока.
*   **Ограниченное время жизни (Bounded Lifetime):** Данные гарантированно уничтожаются в памяти, как только выполнение выходит из лямбда-блока `.run()`. Метод очистки `.remove()` больше не нужен.
*   **Бесплатное наследование:** При порождении дочерних потоков (через Structured Concurrency) `ScopedValue` не копирует данные, а дает дочерним потокам прямую ссылку на ту же область памяти родителя.

### 💣 Ловушки на собеседованиях (Interview Traps)

*   ❌ **Вопрос:** «Является ли `ThreadLocal` теперь устаревшим (Deprecated) в Java 25? Заменит ли ScopedValue его на 100%?»
*   ✅ **Ответ:** **Нет, `ThreadLocal` не помечен как deprecated.** Это не прямая замена. `ThreadLocal` по-прежнему эффективен в классических пулах тяжелых платформенных потоков ОС (например, для кэширования не-потокобезопасных объектов типа `SimpleDateFormat`). `ScopedValue` создан специально для сценариев **однонаправленной передачи контекста сверху вниз** в условиях конкуренции миллионов виртуальных потоков, где критически важна иммутабельность и автоматический контроль памяти.

*   ❌ **Вопрос:** «Напишите код передачи контекста пользователя через Scoped Values».
*   ✅ **Ответ:** 
```java
public class SecurityServer {
    // Создаем глобальный ключ контекста
    public static final ScopedValue<User> CURRENT_USER = ScopedValue.newInstance();

    public void handleRequest(Request req) {
        User user = authenticate(req);
        // Привязываем значение к скоупу выполнения
        ScopedValue.where(CURRENT_USER, user).run(() -> {
            // Внутри этой лямбды любой метод глубоко в call-stack имеет доступ к данным
            businessOrderService.process();
        }); 
        // В этой точке CURRENT_USER автоматически стерт из памяти!
    }
}

// Глубоко внутри логики:
User user = SecurityServer.CURRENT_USER.get(); // Чтение данных
```
