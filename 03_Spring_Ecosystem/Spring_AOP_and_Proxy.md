# 🎭 Spring AOP: Внутренности Прокси и Ловушки Аннотаций
#spring #aop #architecture #mid-senior

### 🎯 Главный инсайт (TL;DR)
> Почти вся декларативная магия Spring (`@Transactional`, `@Async`, `@Cacheable`, `@Secured`) работает на паттерне **Proxy (Прокси)**. Spring не изменяет ваш оригинальный класс в рантайме, а создает вокруг него обертку-перехватчик. Непонимание этого механизма ведет к багам с «молчаливым» отказом транзакций.

### ⚙️ Архитектурные особенности (Under the Hood)

#### 1. Два типа прокси: JDK Dynamic Proxy vs CGLIB
Spring умеет генерировать прокси-классы двумя способами:
*   **JDK Dynamic Proxy:** Используется, если ваш целевой класс реализует хотя бы один интерфейс. Прокси создается средствами самой Java, динамически реализуя тот же интерфейс. Он делегирует вызовы через `InvocationHandler`.
*   **CGLIB (Code Generation Library):** Используется, если у класса нет интерфейсов (или включена принудительная настройка). CGLIB генерирует байт-код на лету, создавая **класс-наследник (subclass)** от вашего целевого класса.

**Важное изменение:** Начиная со Spring Boot 2.x и в **Spring Boot 3.x**, CGLIB используется **по умолчанию для всех бинов**, даже если у них есть интерфейсы (`spring.aop.proxy-target-class=true`). Это снизило количество ошибок при приведении типов.

```text
JDK Dynamic Proxy:
[Interface] <── [Proxy Class] ──> [Your Target Class]

CGLIB Proxy:
[Your Target Class] <── [Proxy Subclass (Generated)]
```

#### 2. Анатомия вызова через Прокси
Когда сторонний бин вызывает метод, помеченный, например, `@Transactional`:
1. Вызов принимает класс-прокси.
2. Прокси обращается к `PlatformTransactionManager` и открывает транзакцию в БД.
3. Прокси вызывает метод внутри вашего реального объекта.
4. Метод отрабатывает.
5. Прокси возвращает управление, делает `commit()` (или `rollback()`, если вылетело исключение) и закрывает транзакцию.

### 💣 Ловушки на собеседованиях (Interview Traps)

*   ❌ **Вопрос:** «Внутри класса `OrderService` есть публичный метод `createOrder()`. Из него внутри этого же класса вызывается другой публичный метод `saveToDb()`, помеченный `@Transactional`. Откроется ли транзакция при вызове `createOrder()` из контроллера?»
*   ✅ **Ответ:** **Нет, транзакция не откроется.** Это классическая ловушка **Self-Invocation (самовызов)**. Контроллер вызывает метод `createOrder()` через прокси-обертку. Но как только управление попало внутрь реального объекта `OrderService`, все последующие внутренние вызовы через ключевое слово `this` идут в обход прокси. Spring просто не сможет перехватить вызов `saveToDb()`.
*   💡 **Как лечить:**
    1. Вынести метод `saveToDb()` в отдельный бин (лучший путь по SOLID).
    2. Внедрить `OrderService` сам в себя через `@Autowired @Lazy` (Self-injection) и вызывать метод через это поле.
    3. Использовать `AopContext.currentProxy()` (требует явного включения в конфигах, считается код-пахом).

*   ❌ **Вопрос:** «Будет ли работать аннотация `@Transactional`, если повесить ее на `private` или `protected` метод?»
*   ✅ **Ответ:** **Нет, не будет.** И JDK Dynamic Proxy, и CGLIB могут переопределять только те методы, к которым у них есть доступ извне. CGLIB создает наследника, поэтому он физически не может переопределить `private` метод родителя. Spring AOP молча проигнорирует эту аннотацию, и код выполнится без транзакции. Более того, методы, помеченные как `final`, CGLIB переопределить также не сможет.
