# Spring Modulith
#spring #microservices

#Links: https://proselyte.net/spring-modulith/

## 1. Что такое Spring Modulith (Коротко)
**Spring Modulith** — это официальное расширение экосистемы Spring, предназначенное для создания **модульных монолитов** (Modular Monoliths). 
Это реальная библиотека, которая помогает разработчикам структурировать код внутри одного приложения так, чтобы логические модули были изолированы друг от друга, а архитектурные правила проверялись автоматически через тесты.

---

## 2. Какую проблему решает? (Зачем он нужен)
* **Проблема классического монолита ("Big Ball of Mud"):
** Со временем слои (Controller -> Service -> Repository) переплетаются. Разработчики начинают случайно вызывать методы из чужих доменов, превращая код в спагетти.
* **Проблема микросервисов:** Микросервисы дают изоляцию, но приносят огромную сложность (сеть, распределенные транзакции, сложный деплой, высокие затраты на инфраструктуру).
* **Решение Spring Modulith:** Дает изоляцию кода (как в микросервисах), но оставляет приложение внутри единого рантайма и одной базы данных (как в монолите).

## 3. Ключевые концепции и термины

### А. Определение модуля (Application Module)
Модулем в Spring Modulith считается **пакет первого уровня**, находящийся сразу под главным пакетом с аннотацией `@SpringBootApplication`.
Проект Spring Modulith, призван поддержать разработчиков в построении domain-driven монолитов, разделенных на логические модули. Иными словами, Spring Modulith помогает “выровнять” структуру кода по доменным областям (например, модуль “Платежи”, модуль “Счета”, модуль “Отчеты” и т.д.),

### Б. Правила инкапсуляции (Видимость)
По умолчанию в Spring Modulith:
* Всё, что лежит в корневом пакете модуля (например, `com.example.myapp.order`), считается **публичным API** этого модуля. Другие модули могут это вызывать.
* Всё, что лежит в подпакете `internal` (например, `com.example.myapp.order.internal`), считается **строго приватным**. Если код из модуля `inventory` попытается импортировать класс из `order.internal`, Spring Modulith завалит тесты.

## 4. Главные фичи фреймворка (Что отвечать на собеседовании)

1. **Архитектурное тестирование (Verification):**
   Вместо ручного контроля кода пишутся ArchUnit-тесты, которые проверяют, что модули не нарушают границы друг друга и в них нет циклических зависимостей.
   ```java
   ApplicationModules modules = ApplicationModules.of(MyApplication.class);
   modules.verify(); // Упадет, если нарушены правила инкапсуляции или есть циклы
   ```

2. **Событийное взаимодействие (Event-Driven Inside Monolith):**
   Чтобы модули не вызывали друг друга напрямую через бины (tight coupling), они общаются через события (`ApplicationEventPublisher`). Spring Modulith берет на себя управление транзакциями при публикации событий.

3. **Журнал событий (Event Publication Registry):**
   Гарантирует доставку событий (Паттерн Outbox). Если в момент публикации события (например, `OrderCreatedEvent`) упал обработчик в модуле `inventory`, Spring Modulith сохранит это событие в БД и попробует переотправить его позже.

4. **Авто-документация:**
   Умеет автоматически генерировать диаграммы компонентов в формате PlantUML на основе структуры вашего кода. Документация всегда актуальна, так как создается во время сборки.

## 5. Топ-вопросы на собеседовании и ответы на них

### Вопрос 1: Чем Spring Modulith отличается от разбиения проекта на Gradle/Maven multi-modules?
**Ответ:** 
Multi-module в Maven/Gradle изолирует код на этапе компиляции, но не решает проблему связности внутри рантайма. К тому же, создавать десятки maven-модулей тяжело инфраструктурно. Spring Modulith позволяет разбить монолит на модули внутри **одного** Gradle/Maven модуля, управляя границами на уровне пакетов Java. Также Maven/Gradle не имеют встроенного Event Publication Registry для надежной работы с событиями.

### Вопрос 2: Как связать два модуля, если им нужна строгая транзакционность?
**Ответ:** 
Лучшая практика — использовать асинхронные события с аннотацией `@TransactionalEventListener`. При этом публикация события происходит в рамках транзакции первого модуля, а обработка — в новой транзакции второго. Если обработка упадет, механизм Event Publication Registry от Spring Modulith гарантирует, что событие не потеряется и будет обработано повторно.

### Вопрос 3: Обязательно ли называть пакеты именно `internal`?
**Ответ:** 
По умолчанию `internal` — это стандартное соглашение. Однако конфигурацию можно кастомизировать с помощью аннотации `@NamedInterface` или файла `package-info.java`, чтобы явно указать, какие части пакета являются открытым API, а какие скрыты.

### Вопрос 4: Как Spring Modulith помогает при переходе на микросервисы?
**Ответ:**
Он служит идеальным промежуточным шагом. Если вы решите вынести модуль `inventory` в отдельный микросервис, вам не придется распутывать спагетти-код. Вы просто берете изолированный пакет, API которого уже определено, а коммуникация уже построена на событиях, и переносите его в отдельный репозиторий.

## 6. Шпаргалка по аннотациям и классам
* `ApplicationModules.of(Class)` — точка входа для анализа структуры проекта в тестах.
* `@ApplicationModuleListener` — сокращение для асинхронного транзакционного слушателя событий (`@Async` + `@TransactionalEventListener`).
* `@NamedInterface` — позволяет объявить кастомное имя для публичного подпакета (вместо экспорта всего корневого пакета).
