# Архитектура и особенности Spring Data JDBC
#jpa #jdbc #spring
### 1. Философия фреймворка
Spring Data JDBC — это концептуальный отказ от сложности Hibernate в пользу предсказуемости. Он создавался как легковесная альтернатива, строго следующая принципам **Domain-Driven Design (DDD)**.

Здесь **нет**:
* Кэша первого и второго уровня (Persistence Context).
* Отслеживания состояний объектов (Proxy, Lazy Loading, Dirty Checking).
* Сессий и отложенных `flush` в базу.

---

### 2. Концепция Агрегатов (Aggregate Root)
В Spring Data JDBC сущности группируются в **Агрегаты**:
* Есть главный объект — **Aggregate Root** (Корень агрегата). Только для него создается `Repository`.
* Есть зависимые сущности. Они не могут существовать без корня.
* **Важное правило**: При изменении любой части агрsегата, Spring Data JDBC лезет в базу и обновляет/перезаписывает агрегат целиком.

> ⚠️ **Особенность работы с коллекциями**: Если у вас есть связь «Один-ко-многим» внутри агрегата, то при обновлении корня Spring Data JDBC сначала выполнит `DELETE` для всех дочерних записей в БД, а затем `INSERT` для текущих элементов из Java-коллекции. Это плата за отсутствие отслеживания состояний.

---

### 3. Как происходят запросы?
1. Вы вызываете `repository.save(user)`.
2. Фреймворк смотрит, есть ли у объекта ID. Если ID нет — выполняется `INSERT`. Если ID есть — выполняется `UPDATE`.
3. Запрос сразу уходит в базу через `NamedParameterJdbcTemplate`.
4. Объекты в Java выступают как простые структуры данных (Data Holders / Records). Никакой магии за спиной разработчика не происходит.

---

### 4. Топ вопросов на интервью по Spring Data JDBC
* **Как реализовать связь Many-to-Many?** Напрямую через аннотации нельзя (в отличие от JPA). Нужно явно создавать промежуточную сущность-таблицу и делать ее частью агрегата, либо ссылаться по ID (`AggregateReference`).
* **Почему Spring Data JDBC работает быстрее на старте приложения?** Ему не нужно сканировать весь мета-граф сущностей, строить сложные абстракции и генерировать тяжелые прокси-классы при запуске Spring Context.

### 4. Что спрашивают на собеседовании

**Почему появился JdbcClient?**
Чтобы убрать многословность JdbcTemplate и NamedParameterJdbcTemplate и дать современный fluent API.

**JdbcClient быстрее JdbcTemplate?**
Нет. Он использует JdbcTemplate внутри, поэтому производительность практически одинаковая.

**Когда использовать JDBC вместо JPA?**
Это уже любимый вопрос на Senior-собеседованиях.

Обычно JDBC (JdbcTemplate/JdbcClient) выбирают когда:

сложные SQL-запросы;
отчёты и аналитика;
высокая нагрузка;
нужен полный контроль над SQL;
ORM даёт слишком большой overhead.

JPA выбирают когда важнее работа с объектной моделью и бизнес-сущностями, чем ручное управление SQL.
