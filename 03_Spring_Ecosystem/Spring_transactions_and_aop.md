# Управление транзакциями в Spring и магия АОР-Прокси

### 1. Архитектура `@Transactional`: Как это работает под капотом
Аннотация `@Transactional` реализуется с помощью Spring AOP (Aspect-Oriented Programming). Когда Spring видит эту аннотацию над классом или методом, он не создает обычный Java-объект. Он создает вокруг него **Объект-Прокси (Proxy)**.

#### Цепочка вызова при обращении к бину:
1. Клиентский код вызывает метод `userService.createUser()`.
2. Вызов перехватывает **Spring Proxy** (созданный через `CGLIB` или `JDK Dynamic Proxy`).
3. Прокси обращается к `PlatformTransactionManager`, берет соединение из пула (DataSource) и открывает физическую транзакцию в БД (`connection.setAutoCommit(false)`).
4. Прокси передает вызов внутрь вашего реального метода `createUser()`.
5. Если метод завершился успешно ➡️ Прокси вызывает `connection.commit()`.
6. Если внутри метода вылетело исключение ➡️ Прокси вызывает `connection.rollback()`.

#### ⚠️ Главный капкан интервью: Самовызов (Self-Invocation)
**Вопрос:** Что произойдет, если вызвать метод с `@Transactional` из другого метода того же самого класса?

```java
@Service
public class UserService {

    public void registerUser(User user) {
        // ... какая-то бизнес-логика ...
        saveData(user); // Вызов метода внутри того же класса!
    }

    @Transactional
    public void saveData(User user) {
        userRepository.save(user);
    }
}
```

**Ответ:** Транзакция **НЕ откроется**. Вызов идет в обход Прокси-обертки, напрямую из реального объекта в реальный метод. Spring AOP физически не может перехватить этот внутренний вызов `this.saveData()`. 

* **Как чинить:**
  1. Вынести метод `saveData` в отдельный компонент/сервис.
  2. Использовать программное управление транзакциями через `TransactionTemplate` вместо аннотации.
  3. *(Специфично для Spring)* Сделать Self-injection (внедрить `UserService` сам в себя через `@Autowired`), чтобы вызывать метод через проксированный бин.

### 2. Распространение транзакций (Transaction Propagation)
Определяет поведение транзакции, если один метод с `@Transactional` вызывает другой метод с `@Transactional`. Настраивается через `@Transactional(propagation = Propagation....)`.

* **REQUIRED (По умолчанию)**
  * Если транзакции еще нет, Spring создает новую. Если транзакция уже открыта вызывающим методом, текущий метод подключается к ней.
  * *Следствие:* Если вложенный метод выбросит исключение, вся общая транзакция будет помечена на откат (`rollback-only`).
* **REQUIRES_NEW**
  * Spring **всегда** создает новую физическую транзакцию для этого метода. Если была внешняя транзакция, она приостанавливается (suspend) до завершения новой.
  * *Зачем нужно:* Для независимых логов или аудита. Вы хотите записать в базу лог попытки действия пользователя, даже если основная бизнес-транзакция упадет и откатится.
* **NESTED**
  * Создает "вложенную" транзакцию с использованием точек сохранения (**Savepoints** базы данных).
  * *Зачем нужно:* Если вложенный метод падает, мы можем откатить базу только до точки старта этого метода, сохранив результаты работы внешнего метода. (Важно: Hibernate это полноценно НЕ поддерживает, работает в основном с чистым JDBC).
* **MANDATORY**
  * Метод требует обязательного наличия открытой внешней транзакции. Если её нет — Spring сразу выбросит исключение.
* **NEVER**
  * Метод требует, чтобы транзакции вообще не было. Если транзакция активна — вылетает исключение.
* **SUPPORTS / NOT_SUPPORTED**
  * `SUPPORTS` — если транзакция есть, метод выполнится в ней. Если нет — выполнится как обычный код без транзакции.
  * `NOT_SUPPORTED` — если транзакция есть, Spring приостанавливает её на время работы метода и выполняет его без транзакции.

### 3. Топ вопросов на интервью по транзакциям в Spring

* **Откатится ли транзакция, если метод выбросит Checked Exception (например, `IOException`)?**
  * *Ответ:* **Нет!** По умолчанию Spring откатывает транзакции автоматически только при `RuntimeException` (непроверяемых) и `Error`. Чтобы транзакция откатывалась при Checked исключениях, нужно явно указывать параметр: `@Transactional(rollbackFor = Exception.class)`. Это один из самых частых вопросов на собеседованиях.

* **В чем разница между `CGLIB` и `JDK Dynamic Proxy` при создании транзакционных бинов?**
  * *Ответ:* `JDK Dynamic Proxy` встроен в Java, работает на уровне рефлексии и может проксировать классы только в том случае, если они реализуют **интерфейсы**. `CGLIB` создает прокси «на лету» в рантайме путем генерации подкласса (bytecode generation). Он используется Spring Boot по умолчанию, так как позволяет проксировать обычные классы без интерфейсов, но у него есть ограничение: он не может перехватывать `final` или `private` методы.
