# ⚡ Архитектура Redis: Структуры данных и Стратегии кэширования
#redis #cache #architecture #high-load #senior

### 🎯 Главный инсайт (TL;DR)
> Redis — это ультрабыстрое In-Memory хранилище данных, высокая скорость которого обеспечивается однопоточной архитектурой (Single-Threaded Event Loop), исключающей затраты на контекст-свитчинг и блокировки потоков CPU. Основной компромисс Redis — риск потери данных при сбоях из-за асинхронного сброса на диск.

### ⚙️ Архитектурные особенности (Under the Hood)

#### 1. Однопоточность и многопоточность в Redis
*   **Исторический движок:** До версии 6.0 Redis выполнял абсолютно все команды строго в одном главном потоке.
*   **Современный Redis (6.0+):** Появились фоновые потоки (Threaded I/O), но они занимаются исключительно парсингом сетевых пакетов, чтением и записью в сокеты. Сама обработка команд и манипуляции со структурами данных в памяти по-прежнему выполняются **в одном главном потоке**. Это гарантирует атомарность выполнения любых одиночных команд без использования Locks.

#### 2. Механизмы персистентности (Сохранение на диск)
Redis может сохранять данные на диск двумя путями:
*   **RDB (Redis Database Snapshot):** Создание снапшота (слепка) всей памяти на диск с определенным интервалом (например, раз в 5 минут). Работает через системный вызов `fork()`. Плюсы: компактный файл, быстрый старт сервера. Минусы: при падении сервера теряются данные за последние N минут.
*   **AOF (Append Only File):** Логирование каждой изменяющей команды в конец файла на диске. Плюсы: максимальная надежность (через `fsync`). Минусы: файл разрастается до огромных размеров, требует периодической перезаписи (AOF Rewrite).

#### 3. Алгоритмы вытеснения данных (Eviction Policies)
Когда память сервера забивается до лимита (`maxmemory`), Redis начинает удалять старые ключи по одной из стратегий:
*   `volatile-lru` / `allkeys-lru`: Удаляет ключи, которые **дольше всего не использовались** (Least Recently Used).
*   `volatile-lfu` / `allkeys-lfu`: Удаляет ключи, которые используются **реже всего** (Least Frequently Used) на основе счетчика частоты вызовов.
*   `noeviction`: Возвращает ошибку на любые попытки записи. Поведение по умолчанию.
*   **Практическая реализация паттерна:** Как спроектировать структуру LRU-кэша с нуля за $O(1)$ на чтение и запись, смотри в файле [[LRU_Cache]] [INDEX].

### 💣 Ловушки на собеседованиях (Interview Traps)

*   ❌ **Вопрос:** «Что такое Cache Avalanche (Лавина кэша) и Cache Stampede (Пробой кэша)? Как от них защититься на бэкенде?»
*   ✅ **Ответ:** 
    *   **Cache Avalanche:** Ситуация, когда у огромного количества популярных ключей одновременно истекает срок жизни (TTL). Бэкенд внезапно теряет кэш для миллионов пользователей и вся лавина запросов идет напрямую в реляционную БД, намертво роняя её. 
        *   💡 *Решение:* Добавлять к TTL небольшой случайный сдвиг (Random Noise / Jitter), чтобы ключи протухали равномерно по времени.
    *   **Cache Stampede:** Ситуация, когда один «тяжелый» ключ (вычисление которого в БД занимает секунды) протухает, и в этот же миг тысячи параллельных потоков видят, что кэша нет, и одновременно бегут в БД вычислять одно и то же значение.
        *   💡 *Решение:* Использовать мьютексы/блокировки в коде приложения (например, `Distributed Lock` через Redlock или локальный `computeIfAbsent`), чтобы только один поток пошел обновлять кэш, а остальные ждали.

*   ❌ **Вопрос:** «У нас есть команда, которая выгребает все ключи по маске: `KEYS user:*`. Безопасно ли запускать её на production-сервере под высокой нагрузкой?»
*   ✅ **Ответ:** **Категорически запрещено.** Так как Redis однопоточный, выполнение O(N) операции `KEYS` заблокирует этот единственный поток на время сканирования миллионов ключей в памяти. Все остальные запросы от пользователей (даже простые `GET`) встанут в очередь и начнут падать по таймауту. 
    *   💡 *Как лечить:* На проде нужно использовать команду **`SCAN`**, которая возвращает данные порциями (итеративно) и не блокирует сервер.
