# 🗄️ Индексы БД, Уровни Изоляции и Архитектура MVCC
#sql #databases #acid #senior

### 🎯 Главный инсайт (TL;DR)
> Уровни изоляции транзакций в современных реляционных СУБД (PostgreSQL, MySQL) редко реализуются через тяжелые физические блокировки строк (пессимизм). Вместо этого используется механизм **MVCC (Multi-Version Concurrency Control)**, который позволяет читать данные без блокировок, создавая под каждую транзакцию виртуальные моментальные снимки (Snapshots).

### ⚙️ Архитектурные особенности (Under the Hood)

#### 1. Аномалии параллельного доступа
Стандарт SQL определяет 4 классические проблемы, которые возникают, когда две транзакции работают одновременно:
1.  **Dirty Read (Грязное чтение):** Транзакция А читает данные, измененные транзакцией Б, которая еще не закоммитилась (не зафиксирована). Если Б сделает Rollback — данные А станут фейком.
2.  **Non-Repeatable Read (Неповторяющееся чтение):** Транзакция А читает строку. Транзакция Б изменяет или удаляет эту строку и делает Commit. Транзакция А читает эту же строку снова и видит изменившиеся данные.
3.  **Phantom Read (Фантомное чтение):** Транзакция А делает выборку диапазона строк (например, `WHERE age > 18`). Транзакция Б *вставляет новую строку* в этот диапазон и делает Commit. Транзакция А повторяет запрос и видит новые «фантомные» строки.
4.  **Serialization Anomaly (Аномалия сериализации):** Результат успешного параллельного выполнения нескольких транзакций не совпадает ни со свободным порядком их поочередного выполнения.

#### 2. Как работает MVCC (на примере PostgreSQL)
В PostgreSQL строки в таблице никогда не обновляются на месте и физически не удаляются сразу:
*   При `UPDATE` старая версия строки помечается как «мертвая» (устанавливается системный флаг скрытого поля `xmax`), а рядом записывается абсолютно новая версия строки (`xmin`).
*   Каждая транзакция при старте получает свой уникальный `TxID`. На основе этого ID движок БД решает, какие версии строк транзакция имеет право видеть, а какие для нее еще «из будущего» или уже удалены.
*   Очисткой старых, ненужных версий строк занимается фоновый процесс **VACUUM**.

#### 3. B-Tree vs LSM-Tree индексы
Индексы определяют, как СУБД ищет данные на диске:
*   **B-Tree (B+Tree):** Сбалансированное дерево, используемое по умолчанию в PostgreSQL/MySQL. Все данные хранятся в листовых нодах, дерево имеет малую глубину. Идеально подходит для **Read-heavy** нагрузок (быстрый поиск по ключу и диапазону за $O(\log N)$). Изменения требуют перезаписи блоков на диске случайным образом (Random I/O).
*   **LSM-Tree (Log-Structured Merge-Tree):** Используется в NoSQL (Cassandra, RocksDB, ScyllaDB). Записи сначала буферизуются в оперативной памяти (MemTable), а затем последовательно (Sequential I/O) сбрасываются на диск в виде неизменяемых файлов (SSTables). Экстремально эффективно для **Write-heavy** нагрузок (логирование, метрики), но чтение происходит медленнее, так как приходится проверять несколько файлов на диске.

### 💣 Ловушки на собеседованиях (Interview Traps)

*   ❌ **Вопрос:** «Каков уровень изоляции транзакций по умолчанию в PostgreSQL, и защищает ли он от фантомного чтения?»
*   ✅ **Ответ:** По умолчанию в PostgreSQL установлен уровень **Read Committed**. Однако, если вы переключите его на уровень **Repeatable Read**, то в отличие от стандарта SQL и других СУБД (например, Oracle), реализация MVCC в PostgreSQL на уровне `Repeatable Read` **полностью защищает от фантомного чтения!** Вам не нужно включать самый тяжелый уровень `Serializable` для борьбы с фантомами в Postgres.

*   ❌ **Вопрос:** «Два потока параллельно запускают Spring-методы с `@Transactional`. Внутри каждого метода происходит списание денег: 1) Читаем баланс (`SELECT balance...`), 2) Вычитаем 100 рублей в Java, 3) Записываем баланс обратно (`UPDATE...`). Защитит ли уровень Repeatable Read от потери денег (аномалия Lost Update)?»
*   ✅ **Ответ:** **Нет, не защитит.** На уровне `Repeatable Read` обе транзакции прочитают один и тот же исходный баланс (например, 1000 руб). Обе транзакции посчитают в Java результат (900 руб). Та транзакция, которая попытается сделать `UPDATE` второй, в Postgres упадет с ошибкой сериализации (`could not serialize access due to concurrent update`). В MySQL она просто затрет изменения первой транзакции.
*   💡 **Как лечить:** Использовать атомарный апдейт на уровне базы: `UPDATE account SET balance = balance - 100 WHERE id = :id` или применять пессимистическую блокировку строки через `SELECT ... FOR UPDATE`.
