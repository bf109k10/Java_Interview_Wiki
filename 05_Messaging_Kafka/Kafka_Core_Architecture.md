# ⚙️ Архитектура ядра Apache Kafka: Партиции и Ребалансировка

### 🎯 Главный инсайт (TL;DR)
> Масштабируемость Kafka держится на жестком физическом разделении топиков на **партиции (Partitions)**, каждая из которых представляет собой неизменяемый последовательный лог дозаписи (Append-Only Log) на диске. Параллельное чтение обеспечивается механизмом **Consumer Groups**, где одна партиция в один момент времени может читаться строго одним консьюмером из группы.

### ⚙️ Архитектурные особенности (Under the Hood)

#### 1. Устройство Партиций и Офсетов
*   Каждое сообщение в партиции получает свой порядковый номер — **Offset (офсет)**. Офсеты неизменяемы. Удалить или обновить сообщение в середине партиции невозможно.
*   **Запись на диск (Sequential I/O):** Kafka не пишет данные в случайные места диска. Она делает только `append` в конец файла. Последовательная запись на современные диски (даже HDD) по скорости сопоставима с оперативной памятью, что делает Kafka ультрабыстрой.
*   **Zero-Copy:** При отправке данных консьюмеру Kafka использует системный вызов ОС `sendfile`. Данные копируются напрямую из кэша ОС (Page Cache) в сетевой сокет, минуя буфер приложения Java. Это экономит CPU и память.

#### 2. Группы консьюмеров (Consumer Groups)
Если вам нужно обрабатывать терабайты данных из одного топика, вы запускаете несколько экземпляров своего сервиса с одинаковым `group.id`.
*   Если партиций 4, а консьюмеров в группе 2 — каждый консьюмер получит по 2 партиции.
*   Если консьюмеров станет 4 — каждый заберет по 1 партиции (максимальный параллелизм).
*   Если консьюмеров станет 5 — один будет просто простаивать (Idle), так как Kafka запрещает двум консьюмерам из *одной группы* читать *одну партицию* одновременно (это сломало бы порядок обработки сообщений).

```text
Топик (4 Партиции):  [P 0]   [P 1]   [P 2]   [P 3]
                       │       │       │       │
                       ▼       ▼       ▼       ▼
Consumer Group (2 C):  [ Консьюмер А ]  [ Консьюмер Б ]
```

#### 3. Механизм Ребалансировки (Rebalance)
Когда в группе меняется состав (поднялся новый под сервиса или один из подов упал), Kafka инициирует **ребалансировку** — процесс перераспределения партиций между оставшимися консьюмерами.
*   За процессом следит один из брокеров — **Group Coordinator**.
*   Консьюмеры постоянно шлют ему сигналы жизни (Heartbeats). Если консьюмер не прислал хартбит в течение `session.timeout.ms`, координатор считает его мертвым и объявляет ребаланс.
*   **Проблема:** Во время классического ребаланса (Eager Protocol) происходит фаза **Stop-The-World для всей группы**: все консьюмеры перестают читать данные, отдают свои партиции и ждут, пока координатор нарежет их заново. В современных версиях Kafka этот процесс оптимизировали через протокол **Cooperative Sticky**, который переназначает только изменившиеся партиции, не останавливая остальных.

### 💣 Ловушки на собеседованиях (Interview Traps)

*   ❌ **Вопрос:** «Мой микросервис вычитал пачку сообщений из Kafka. Обработка одного тяжелого сообщения заняла 10 минут (например, долгий расчет). В этот момент вся моя Consumer Group внезапно ушла в бесконечный ребаланс. Почему это произошло? Хартбиты-то отправлялись в фоне отдельным потоком Kafka-клиента!»
*   ✅ **Ответ:** Вы поймали ловушку параметра **`max.poll.interval.ms`**. 
*   Внутри Kafka-клиента поток, отправляющий хартбиты (`session.timeout.ms`), действительно работает независимо. Но у Kafka есть вторая проверка на уровне логики: если ваш основной бизнес-поток застрял на обработке и долго не вызывает следующий метод `.poll()`, брокер делает вывод: «Поток обработки завис / случился дедлок, консьюмер недееспособен». 
*   Если время между двумя вызовами `.poll()` превысило лимит `max.poll.interval.ms` (по умолчанию обычно 5 минут), брокер принудительно выкидывает этот экземпляр из группы и запускает ребаланс.
*   💡 **Как лечить:** 
    1. Увеличить `max.poll.interval.ms` в конфигах.
    2. Уменьшить размер пачки забираемых данных (`max.poll.records`).
    3. Уводить тяжелую обработку в собственный фоновый пул потоков (или Виртуальные потоки), вовремя делая `.poll()`.
