## 1. Strangler Fig (Удушающее дерево)

### Назначение
Постепенная миграция монолита в микросервисную архитектуру без Big Bang-переписывания.

### Идея
1. Перед монолитом создается фасад (proxy/gateway).
2. Все запросы проходят через него.
3. Функциональность постепенно переносится в новые сервисы.
4. Фасад начинает перенаправлять часть запросов в новые сервисы.
5. Монолит постепенно уменьшается и в итоге удаляется.

### Плюсы
- Минимизация рисков миграции.
- Отсутствие длительного простоя.
- Возможность отката.
- Поэтапное тестирование.

### Минусы
- Долгое сосуществование двух архитектур.
- Необходимость четкого определения границ сервисов.

### Когда применять
- Большие legacy-монолиты.
- Постепенный переход на микросервисы.

## 2. API Gateway

### Назначение
Единая точка входа для клиентов.

### Идея
Клиент взаимодействует только со шлюзом, который:
- маршрутизирует запросы;
- агрегирует ответы;
- выполняет инфраструктурные функции.

### Возможности
- Аутентификация и авторизация.
- SSL/TLS termination.
- Логирование.
- Мониторинг.
- Балансировка нагрузки.
- Кэширование.
- Rate limiting.
- Трансформация протоколов.

### Варианты использования

#### Gateway Routing
Простая маршрутизация запросов.

#### Gateway Aggregation
Объединение данных из нескольких сервисов.

#### Gateway Offloading
Вынесение общей инфраструктурной логики.

### Плюсы
- Одна точка входа.
- Скрытие внутренней структуры системы.
- Централизация общей логики.
- Уменьшение количества клиентских запросов.

### Минусы
- Single Point of Failure.
- Возможное узкое место по производительности.
- Усложнение отладки.
- Дополнительная задержка.

### Популярные решения
- NGINX
- Kong
- KrakenD
- HAProxy
- Traefik
- AWS API Gateway

## 3. Service Mesh

### Назначение
Управление взаимодействием сервисов на сетевом уровне.

### Структура

#### Data Plane
Прокси рядом с каждым сервисом.

#### Control Plane
Централизованное управление политиками и конфигурацией.

### Возможности
- Маршрутизация.
- Балансировка нагрузки.
- Retry.
- Circuit Breaker.
- mTLS.
- Service-to-Service Authentication.
- Метрики.
- Логирование.
- Distributed Tracing.

### Плюсы
- Надежность.
- Безопасность.
- Наблюдаемость.
- Единые сетевые политики.
- Меньше инфраструктурного кода в сервисах.

### Минусы
- Сложность эксплуатации.
- Дополнительное потребление ресурсов.
- Повышенная задержка.
- Требует зрелой DevOps-практики.

### Популярные решения
- Istio
- Linkerd
- Consul Connect
- AWS App Mesh
- Kuma

### Когда применять
- Десятки и сотни сервисов.
- Kubernetes-кластеры.
- Высокие требования к observability.

## 4. Sidecar

### Назначение
Вынесение вспомогательной функциональности из приложения в отдельный процесс или контейнер.

### Идея
Основное приложение отвечает только за бизнес-логику.

Дополнительные задачи выполняет sidecar:
- логирование;
- мониторинг;
- конфигурация;
- проксирование;
- интеграции.

### Типичные сценарии
- Log shipper.
- Конфигурационный агент.
- Ambassador proxy.
- Service Mesh proxy.

### Плюсы
- Разделение ответственности.
- Повторное использование.
- Независимые обновления.
- Технологическая независимость.

### Минусы
- Дополнительное потребление ресурсов.
- Усложнение деплоя.
- Необходимость синхронизации жизненного цикла.

### Связь с другими паттернами
Service Mesh фактически строится на Sidecar-прокси.

## 5. Database per Service

### Назначение
Изоляция данных между микросервисами.

### Идея
Каждый сервис владеет собственной базой данных.

Другие сервисы не обращаются к ней напрямую.

### Преимущества
- Слабая связанность.
- Независимая эволюция сервисов.
- Независимое масштабирование.
- Локальные транзакции.
- Изоляция отказов.
- Возможность использовать разные типы БД.

### Недостатки
- Сложность межсервисных запросов.
- Отсутствие глобальных транзакций.
- Более сложная консистентность данных.

### Практика
Взаимодействие между данными осуществляется через:
- API;
- события;
- асинхронные сообщения.

---

## 6. CQRS (Command Query Responsibility Segregation)

### Идея
Разделение операций записи и чтения.

### Команды (Commands)
Изменяют состояние системы.

### Запросы (Queries)
Только читают данные.

### Преимущества
- Независимое масштабирование чтения и записи.
- Оптимизация моделей данных.
- Высокая производительность.

### Недостатки
- Более сложная архитектура.
- Необходимость синхронизации моделей.

### Когда применять
- Системы с большим количеством чтений.
- Высоконагруженные системы.

---

## 7. Event Sourcing

### Идея
Хранится не текущее состояние объекта, а последовательность событий.

### Пример
Вместо:

Balance = 1000

Храним:

- AccountCreated
- MoneyDeposited(1000)
- MoneyWithdrawn(200)

Текущее состояние вычисляется путем воспроизведения событий.

### Преимущества
- Полный аудит.
- История изменений.
- Возможность восстановления состояния.
- Хорошая интеграция с CQRS.

### Недостатки
- Сложность реализации.
- Рост объема хранилища.
- Необходимость снапшотов.

### Когда применять
- Финансовые системы.
- Аудит.
- Event-Driven Architecture.

# Interview Questions

## Strangler Fig

### Базовые вопросы

**Что такое Strangler Fig Pattern?**
- Паттерн постепенной миграции монолита в микросервисы через поэтапное замещение функциональности.

**Чем Strangler Fig лучше полного переписывания системы?**
- Ниже риск.
- Быстрее получение результата.
- Можно откатывать отдельные части.
- Не требуется большая миграция одним релизом.

**Как определить границы первых сервисов?**
- Искать bounded contexts.
- Начинать с наиболее изолированных модулей.
- Избегать функциональности с большим количеством зависимостей.

### Продвинутые вопросы

**Какие основные риски Strangler Fig?**
- Дублирование логики.
- Распределенные транзакции.
- Разделение данных между монолитом и сервисами.
- Рост сложности маршрутизации.

**Как организовать совместный доступ к данным монолита и новых сервисов?**
- Предпочтительно через API.
- Временно допустим shared database.
- В долгосрочной перспективе — Database per Service.

## API Gateway

### Базовые вопросы

**Зачем нужен API Gateway?**
- Единая точка входа.
- Маршрутизация.
- Аутентификация.
- Ограничение нагрузки.
- Агрегация запросов.

**Почему нельзя обращаться к сервисам напрямую?**
- Усложнение клиентов.
- Проблемы безопасности.
- Частые изменения внутренней архитектуры.

**Чем API Gateway отличается от Reverse Proxy?**
- Reverse Proxy обычно только маршрутизирует.
- API Gateway содержит бизнес-ориентированные функции:
  - аутентификацию;
  - rate limiting;
  - агрегацию;
  - трансформацию запросов.

### Продвинутые вопросы

**Почему API Gateway может стать Single Point of Failure?**
- Через него проходит весь трафик.
- Поэтому обычно делают несколько экземпляров и балансировку.

**Какие функции не стоит переносить в Gateway?**
- Бизнес-логику.
- Сложные вычисления.
- Доменную валидацию.

**Когда API Gateway становится антипаттерном?**
- Когда в него начинают переносить бизнес-логику.

---

## Service Mesh

### Базовые вопросы

**Что такое Service Mesh?**
- Инфраструктурный слой для взаимодействия сервисов.

**Чем Service Mesh отличается от API Gateway?**

API Gateway:
- North-South traffic.
- Клиент → система.

Service Mesh:
- East-West traffic.
- Сервис → сервис.

**Что такое Sidecar Proxy?**
- Локальный прокси рядом с сервисом.
- Через него проходит весь сетевой трафик.

### Продвинутые вопросы

**Что такое Data Plane и Control Plane?**

Data Plane:
- Envoy/прокси возле сервиса.

Control Plane:
- Управление конфигурацией и политиками.

**Какие задачи обычно решает Mesh?**
- Retry.
- Circuit Breaker.
- mTLS.
- Routing.
- Tracing.

**Почему Mesh не всегда нужен?**
- Усложняет систему.
- Потребляет память и CPU.
- Для 5–10 сервисов может быть избыточным.

## Sidecar

### Базовые вопросы

**Что такое паттерн Sidecar?**
- Вынесение вспомогательной функциональности в отдельный контейнер или процесс.

**Что обычно выносится в Sidecar?**
- Логи.
- Метрики.
- Проксирование.
- Конфигурация.

### Продвинутые вопросы

**Чем Sidecar лучше библиотеки внутри приложения?**
- Независимые обновления.
- Не зависит от языка программирования.
- Единая реализация для всех сервисов.

**Какие недостатки Sidecar?**
- Больше контейнеров.
- Дополнительные ресурсы.
- Сложнее диагностика.

## Database per Service

### Базовые вопросы

**Почему каждому сервису нужна собственная БД?**
- Независимость.
- Слабая связанность.
- Автономное развитие.

**Почему прямой доступ к БД другого сервиса считается плохой практикой?**
- Нарушается инкапсуляция.
- Ломается независимость сервисов.

### Продвинутые вопросы

**Как делать JOIN между данными разных сервисов?**
Обычно:
- API Composition.
- CQRS Read Model.
- Event-Driven Projection.

**Что такое Shared Database и почему это плохо?**
- Несколько сервисов используют одну БД.
- Возникает сильная связанность.

**Как обеспечить согласованность данных?**
- Saga Pattern.
- Eventual Consistency.
- Domain Events.

---

## CQRS

### Базовые вопросы

**Что такое CQRS?**
- Разделение моделей чтения и записи.

**Почему одной модели бывает недостаточно?**
- Запись и чтение часто имеют разные требования.

### Продвинутые вопросы

**Нужно ли использовать разные базы данных для CQRS?**
Нет.
Можно:
- одну БД;
- разные схемы;
- разные БД.

**Какие проблемы решает CQRS?**
- Высокая нагрузка на чтение.
- Сложные запросы.
- Независимое масштабирование.

**Какие проблемы создает CQRS?**
- Сложность.
- Eventual Consistency.
- Дополнительная синхронизация.

---

## Event Sourcing

### Базовые вопросы

**Что хранится в Event Sourcing?**
- События.
- Не текущее состояние объекта.

**Как получить текущее состояние?**
- Воспроизвести последовательность событий.

**Что такое Event Store?**
- Хранилище событий.

### Продвинутые вопросы

**Зачем нужны Snapshots?**
Чтобы не проигрывать тысячи событий при каждом чтении.

**Что делать, если схема события изменилась?**
- Versioning Events.
- Upcasters.
- Поддержка старых версий.

**Какие недостатки Event Sourcing?**
- Сложная отладка.
- Сложные миграции.
- Eventual Consistency.
- Большие объемы данных.

---

## Частые вопросы "на синьора"

### CQRS vs Event Sourcing

CQRS:
- Разделение чтения и записи.

Event Sourcing:
- Способ хранения данных через события.

Они часто используются вместе, но независимы.

---

### API Gateway vs Service Mesh

API Gateway:
- Клиентский трафик.
- North-South.

Service Mesh:
- Межсервисный трафик.
- East-West.

---

### Saga vs Distributed Transaction

2PC:
- Сильная консистентность.
- Плохо масштабируется.

Saga:
- Последовательность локальных транзакций.
- Компенсационные операции.
- Eventual Consistency.

---

### Когда микросервисы хуже монолита?

- Маленькая команда.
- Простая предметная область.
- Низкая нагрузка.
- Нет потребности в независимом масштабировании.

Очень популярный вопрос:
"У вас 10 разработчиков и интернет-магазин средней сложности. Вы сразу выберете микросервисы?"

Ожидаемый ответ:
"Нет. Начал бы с модульного монолита и переходил бы к микросервисам только при появлении конкретных организационных или технических причин."

Из всего списка на собеседованиях уровня Middle/Senior чаще всего спрашивают именно:

API Gateway vs Service Mesh.
Database per Service и как делать JOIN между сервисами.
CQRS vs Event Sourcing.
Saga и eventual consistency (хотя в статье этого паттерна нет, он почти всегда всплывает рядом).
Почему микросервисы могут быть ошибкой для проекта.

Последние два вопроса обычно являются наиболее показательными для уровня Senior, потому что проверяют понимание компромиссов, а не знание терминов.
