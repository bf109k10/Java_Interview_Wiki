# 🕸️ Архитектура Микросервисов: Service Discovery, API Gateway и Service Mesh
#microservices #architecture #infrastructure #senior

### 🎯 Главный инсайт (TL;DR)
> По мере роста количества микросервисов управление сетевыми вызовами, безопасностью (mTLS) и трассировкой усложняется. Эволюция инфраструктуры прошла путь от встроенных библиотек в коде приложения (Netflix OSS) к выделенным платформенным прокси-оберткам инфраструктурного уровня (**Service Mesh / Istio**).

### ⚙️ Архитектурные особенности (Under the Hood)

#### 1. Сервис Дискавери (Service Discovery)
В динамической облачной среде IP-адреса подов микросервисов постоянно меняются (при перезапусках, масштабировании). Чтобы сервисы могли находить друг друга, используется реестр:
*   **Клиентская модель (например, Netflix Eureka / Consul):** При старте микросервис регистрирует свой IP в Eureka. Если Сервису А нужно вызвать Сервис Б, он обращается к Eureka, скачивает список IP-адресов Сервиса Б, кэширует его у себя и сам балансирует запросы (через Spring Cloud LoadBalancer).
*   **Платформенная модель (Kubernetes):** K8s берет эту задачу на себя через внутренний DNS и абстракцию `Service`. Микросервису не нужно знать IP, он просто шлет запрос на имя сервиса в кластере.

#### 2. API Gateway vs Service Mesh
Интервьюеры часто проверяют, понимает ли кандидат разницу в зонах ответственности этих компонентов:
*   **API Gateway (Внешний контур / North-South трафик):** Единая точка входа для внешних клиентов (мобильных приложений, фронтенда) в ваш кластер микросервисов. Занимается аутентификацией (проверкой JWT), глобальным Rate Limiting, маршрутизацией запросов. Примеры: *Spring Cloud Gateway*, *Kong*, *KrakenD*.
*   **Service Mesh (Внутренний контур / East-West трафик):** Сеть управления взаимодействием *между самими микросервисами* внутри кластера. Применяется паттерн **Sidecar (Коляска мотоцикла)**: рядом с каждым контейнером приложения разворачивается крошечный прокси-сервер (например, **Envoy**). Весь сетевой трафик между сервисами идет исключительно через эти Sidecar-прокси.

```text
North-South Traffic:
[Клиент] ──> 🛡️ [API Gateway] ──> [Кластер]

East-West Traffic (Service Mesh):
[Под Сервиса А: Код] <──> [Sidecar Proxy] ──(mTLS)──> [Sidecar Proxy] <──> [Под Сервиса Б: Код]
```

#### 3. Что дает Service Mesh (Istio) инженерам:
1.  **Прозрачный mTLS:** Прокси-серверы автоматически шифруют трафик между собой и проверяют сертификаты. Код самого Java-приложения работает по обычному HTTP и ничего об этом не знает.
2.  **Умная маршрутизация:** Можно легко настроить Canary-релизы (направлять 10% трафика на новую версию сервиса) на уровне конфигов инфраструктуры.
3.  **Телеметрия без кода:** Sidecar собирает метрики и сквозные логи (Tracing) сам, освобождая разработчиков от необходимости подключать библиотеки типа MicroProfile Telemetry / Spring Actuator.

### 💣 Ловушки на собеседованиях (Interview Traps)

*   ❌ **Вопрос:** «Если Service Mesh (Istio) решает столько проблем из коробки, почему бы не внедрять его в любой микросервисный проект с самого первого дня?»
*   ✅ **Ответ:** Это классический пример оверхеда (**Infrastructure Overhead**). Внедрение Service Mesh не дается бесплатно:
    1. **Потребление ресурсов:** Добавление Sidecar-контейнера (Envoy) к каждому поду увеличивает утилизацию памяти кластера и процессора. Если у вас 200 подов, вы развернете 200 дополнительных прокси.
    2. **Сетевые задержки (Latency):** Каждый сетевой пакет теперь делает дополнительные прыжки (hops): из приложения в локальный Sidecar, оттуда по сети в удаленный Sidecar, и только потом в удаленное приложение. Это добавляет миллисекунды к каждому вызову.
    3. **Сложность отладки:** Поиск сетевых проблем становится сложнее, так как между сервисами появляется дополнительный слой абстракции, который нужно администрировать.
    *   💡 **Вывод:** Для 10-20 микросервисов Service Mesh избыточен. Его имеет смысл внедрять на масштабах в сотни сервисов, где ручное управление безопасностью и трассировкой становится невозможным.
