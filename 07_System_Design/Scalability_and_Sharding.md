# 🌐 Масштабирование, Шардирование и Распределенный Консенсус
#system-design #scalability #databases #architecture #senior

### 🎯 Главный инсайт (TL;DR)
> Масштабирование распределенных систем — это всегда управление компромиссами между доступностью и согласованностью данных. Шардирование решает проблему объема данных и физических лимитов одного сервера, но усложняет архитектуру, требуя применения алгоритмов консистентного хэширования и распределенного консенсуса.

### ⚙️ Архитектурные особенности (Under the Hood)

#### 1. Вертикальное vs Горизонтальное масштабирование
*   **Vertical Scaling (Up):** Добавление ресурсов (CPU, RAM, SSD) на текущий сервер. Имеет жесткий физический и финансовый потолок.
*   **Horizontal Scaling (Out):** Добавление новых серверов в кластер. Не имеет ограничений по масштабу, но превращает систему в распределенную, где начинают действовать законы физики (сетевые задержки и сбои).
> 💡 **Микро-паттерн оптимизации памяти:** Эффективное масштабирование начинается с чистоты кода. Паттерн «Два указателя» в задаче [[Valid_Palindrome]] наглядно показывает, как можно обработать массив данных *in-place* за $O(1)$ по памяти, полностью избегая создания лишних объектов в Heap, что на High-Load проектах снижает нагрузку на Garbage Collector.

#### 2. Теоремы CAP и PACELC
*   **CAP Теорема:** В распределенной системе при наличии сетевого расщепления (**P**artition tolerance) мы можем гарантировать либо строгую согласованность данных (**C**onsistency), либо доступность системы (**A**vailability).
*   **PACELC Теорема (Расширение CAP):** Если система работает нормально (без сбоев сети — **P**artition), какой компромисс мы выбираем? Между задержкой (**L**atency) или согласованностью (**C**onsistency)? 
    *   *Пример:* MongoDB выбирает строгую согласованность в ущерб задержкам. Cassandra выбирает минимальную задержку (Eventual Consistency).

#### 3. Шардирование (Sharding) баз данных
Разделение данных одной большой таблицы между независимыми серверами (шардами) по определенному ключу (`Sharding Key`).
*   **Диапазонное (Range-based):** Данные делятся по диапазонам (например, ID от 1 до 1M на Шард 1, от 1M до 2M на Шард 2). Минус: неравномерная нагрузка (Hotspots), если новые пользователи всегда пишутся в последний шард.
*   **Хэш-директивное (Hash-based):** Вычисляется `hash(key) % N`, где N — число шардов. Минус: при добавлении нового шарда (N меняется на N+1) придется перераспределять и перемещать между серверами почти 100% всех данных.

#### 4. Консистентное хэширование (Consistent Hashing)
Решает проблему изменения конфигурации кластера. Хэш-значения шардов и ключей данных проецируются на виртуальное **хэш-кольцо (Hash Ring)** от 0 до 2³²-1. 
* Данные записываются на тот шард, который является ближайшим по часовой стрелке на кольце.
* При добавлении или удалении одного шарда, перемещению подлежит лишь малая часть данных — в среднем K/N (где K — число ключей, N — число шардов).

```text
          [Shard A] (at 12:00)
         /         \
   (Data Key)       [Shard B] (at 4:00)
       |             /
  [Shard C] (at 8:00)
```

### 💣 Ловушки на собеседованиях (Interview Traps)

*   ❌ **Вопрос:** «Мы зашардировали таблицу пользователей по `user_id`. Нам нужно сделать аналитический запрос: посчитать количество пользователей старше 25 лет по всей системе (`SELECT COUNT(*) WHERE age > 25`). Как этот запрос выполнится под капотом?»
*   ✅ **Ответ:** Это худший сценарий для шардированной БД, называемый **Scatter-Gather (разбросать-собрать)**. Так как в запросе нет ключа шардирования (`user_id`), координатор базы данных не знает, на каком сервере лежат нужные строки. Он вынужден отправить этот запрос абсолютно на **все шарды** в кластере. Каждый шард выполнит вычисления, вернет промежуточный результат координатору, и тот соберет их вместе. Это уничтожает производительность и утилизирует весь кластер.
*   💡 **Как лечить:** Для таких запросов данные должны реплицироваться в денормализованном виде в отдельные OLAP-хранилища (ClickHouse, Elasticsearch, BigQuery).

*   ❌ **Вопрос:** «Каким требованиям должен отвечать хороший Sharding Key?»
*   ✅ **Ответ:** Хороший ключ шардирования должен отвечать двум критериям:
    1. **Высокая кардинальность (High Cardinality):** Значения должны быть максимально разнообразными (например, `user_id` или `order_uuid`, но не `gender` или `country_id`), чтобы данные распределялись на сотни серверов, а не группировались в пару куч.
    2. **Равномерное распределение по времени:** Ключ не должен монотонно возрастать (как автоинкрементный `id` или `timestamp`), иначе вся текущая запись в реальном времени будет бомбить только один конкретный сервер (последний шард), создавая Hotspot.
